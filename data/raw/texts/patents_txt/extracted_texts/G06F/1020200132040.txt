기 술 분 야
본 발명은 임베디드 소프트웨어 컴포넌트를 설계하는 방법 및 이를 위한 장치에 관한 발명이다. 구체적으로, 본
[0001]
발명은 임베디드 소프트웨어 시스템의 설계 방법론에 있어서, IEC 61499 국제 표준 Function Block 아키텍처 모
델에 기반을 두면서, 센서-컨트롤러-엑추에이터 설계 패턴이 적용된 컴포넌트 기반 설계 방법 및 이를 위한 장
치에 관한 것이다.
배 경 기 술
임베디드 시스템은 특정 시스템에 내장되어 필요한 제어 기능을 담당하는 컴퓨터 시스템을 의미하며, 해당 컴퓨
[0002]
터 시스템에 장착되는 소프트웨어 시스템을 임베디드 소프트웨어 시스템이라고 한다. 최근 임베디드 시스템의
활용이 확대되면서 임베디드 소프트웨어 시스템의 규모 및 복잡도 또한 증가하고 있다. 그리고, 이에 따른 임베
디드 소프트웨어 시스템의 생산성 및 품질관리가 중요한 문제로 제기되고 있다. 현재 임베디드 소프트웨어 시스
템의 생산성 및 품질관리를 해결하기 위한 방법으로 가장 일반적으로 받아들여지고 있는 방법론 중의 하나가 컴
포넌트 기반 개발 방법론이다.
컴포넌트 기반 개발 방법론이란, 해당 소프트웨어 시스템을 구성하는 구성요소를 마치 하드웨어 시스템의 부품
[0003]
과 같은 개념으로 간주할 수 있는 컴포넌트로 정의하고, 해당 소프트웨어 시스템이 이들 컴포넌트들의 조합이
될 수 있도록 시스템을 설계하고 구현하는 방법론을 의미한다. 이러한 컴포넌트 기반 방법론으로 개발된 각 컴
포넌트는 타 컴포넌트에 대해 독립성을 가지며, 독립성으로 인해 컴포넌트들은 시스템의 개발 및 사후 관리 측
면에서 다음과 같은 장점들을 갖는다.
첫 번째 장점은 재사용성이다. 재사용성이란 이전에 개발되어 품질 검증이 끝난 소프트웨어의 일부 또는 전체를
[0004]
개발 중인 소프트웨어에 사용할 수 있는 특성을 의미한다. 재사용성이 높으면 이전에 개발된 소프트웨어의 경험
과 지식을 개발 중인 소프트웨어에 적용할 수 있으므로, 소프트웨어 개발 품질과 생산성이 높아지고 비용이 감
소할 수 있다.
두 번째 장점은 변경관리 효율성이다. 변경관리란 개발 중이거나 개발이 끝난 소프트웨어에 오류 수정, 성능 향
[0005]
상 그리고 추가 기능 등과 같은 변경사항이 생길 경우 변경이 필요한 소프트웨어의 부분을 찾아내고 수정하는
작업을 의미한다. 컴포넌트 기반 개발 방법론을 사용하는 경우, 수정의 대상이 되는 소프트웨어가 하드웨어 부
품처럼 컴포넌트 단위로 나눠져 있기 때문에, 컴포넌트 단위로 변경사항을 관리할 수 있어 변경관리 효율성을
높일 수 있다.
현재 위와 같은 장점을 가지고 있는 컴포넌트 기반 방법론을 임베디드 소프트웨어 시스템에 효율적으로 적용하
[0006]
기 위하여 국제 표준으로 IEC  61499  Function  Block  아키텍처 모델이 만들어져 사용되고 있다.  하지만 IEC
61499 Function Block 아키텍처 모델 표준에서는 컴포넌트 모델로서 펑션 블록(Function Block)과 이를 이용한
아키텍처 모델은 제시하고 있으나, 임베디드 소프트웨어 시스템을 펑션 블록 컴포넌트 기반으로 설계하는 방법
에 대해서는 명확하게 설명하지 않고 있다.  그러므로 임베디드 소프트웨어 시스템을 설계할 때 IEC  61499
Function Block 아키텍처 모델 표준을 효과적으로 사용하기 위해서는 Function Block 아키텍처 모델을 고려한
효율적인 새로운 설계 방법론이 필요하다.
또한, 임베디드 소프트웨어 시스템은 일반 소프트웨어 시스템과는 다르게 하드웨어 장치 및 하드웨어 구조에 영
[0007]
향을 받으므로 하드웨어에 종속적이다. 이에 따라, 현재 임베디드 소프트웨어 시스템의 컴포넌트 기반 개발 방
법론에 대하여 다양하게 연구되고 있으나, 하드웨어 종속성을 고려한 임베디드 소프트웨어 시스템 컴포넌트 아
키텍처 설계 방법은 아직 제시되지 않고 있다. 이러한 문제를 해결하기 위해서는 하드웨어 종속성을 고려한 새
로운 임베디드 소프트웨어 시스템 컴포넌트 아키텍처 설계 방법론이 필요하다.
한편, 임베디드 소프트웨어 시스템 설계 시 하드웨어 종속성 문제를 해결하기 위한 방법으로 제안되어 널리 사
[0008]
용되는 설계 패턴으로 센서-컨트롤러-엑추에이터(sensor-controller-actuator) 패턴이 있다. 하지만 본 패턴의
적용 효과를 높이기 위해서는 컴포넌트 설계 시 컴포넌트들을 센서, 컨트롤러, 액추에이터 기능으로 분류하고
이들의 연관 관계를 체계적으로 설계할 수 있는 컴포넌트 설계 방법론이 필요하나, 현재 이에 대한 체계적인 설
계 방법은 제시된 바 없다.

해결하려는 과제

[0009]
표준 IEC 61499 Function Block 아키텍처 모델에 기반을 두고, 센서-컨트롤러-엑추에이터 설계 패턴이 적용된
컴포넌트 기반 설계 방법을 제안한다.
이를 위해서, 먼저, 하드웨어 종속성 파악을 위해 센서-컨트롤러-엑추에이터 설계 패턴을 고려한 하드웨어 시스

려하여 센서-컨트롤러-엑추에이터 패턴에 따른 컴포넌트를 추출하는 방법을 제안한다.
본 실시 예에서 제안된 방법은, 추출된 컴포넌트와 하드웨어 시스템 모델 간의 추적성을 보장하기 위해 새롭게

반 설계 방법 및 장치를 제안한다.
본 실시 예가 이루고자 하는 기술적 과제는 상기된 바와 같은 기술적 과제들로 한정되지 않으며, 이하의 실시
[0012]
예들로부터 또 다른 기술적 과제들이 유추될 수 있다.

발명을 실시하기 위한 구체적인 내용
실시 예들에서 사용되는 용어는 본 개시에서의 기능을 고려하면서 가능한 현재 널리 사용되는 일반적인 용어들

있다. 또한, 특정한 경우는 출원인이 임의로 선정한 용어도 있으며, 이 경우 해당되는 설명 부분에서 상세히 그
의미를 기재할 것이다. 따라서 본 개시에서 사용되는 용어는 단순한 용어의 명칭이 아닌, 그 용어가 가지는 의

명세서 전체에서 어떤 부분이 어떤 구성요소를 "포함"한다고 할 때, 이는 특별히 반대되는 기재가 없는 한 다른
[0023]
구성요소를 제외하는 것이 아니라 다른 구성요소를 더 포함할 수 있음을 의미한다.  또한,  명세서에 기재된
 "...부", "...모듈" 등의 용어는 적어도 하나의 기능이나 동작을 처리하는 단위를 의미하며, 이는 하드웨어 또
는 소프트웨어로 구현되거나 하드웨어와 소프트웨어의 결합으로 구현될 수 있다.
명세서 전체에서 기재된 "a, b, 및 c 중 적어도 하나"의 표현은, 'a 단독', 'b 단독', 'c 단독', 'a 및 b', 'a
[0024]
및 c', 'b 및 c', 또는 'a, b, 및 c 모두'를 포괄할 수 있다.
이하에서 언급되는 "단말"은 네트워크를 통해 서버나 타 단말에 접속할 수 있는 컴퓨터나 휴대용 단말로 구현될

수 있다. 여기서, 컴퓨터는 예를 들어, 웹 브라우저(WEB Browser)가 탑재된 노트북, 데스크톱(desktop), 랩톱
(laptop)  등을 포함하고,  휴대용 단말은 예를 들어,  휴대성과 이동성이 보장되는 무선 통신 장치로서,
IMT(International  Mobile  Telecommunication),  CDMA(Code  Division  Multiple  Access),  W-CDMA(W-Code
Division Multiple Access), LTE(Long Term Evolution) 등의 통신 기반 단말, 스마트폰, 태블릿 PC 등과 같은
모든 종류의 핸드헬드(Handheld) 기반의 무선 통신 장치를 포함할 수 있다.
본 개시에서 설명되는 용어를 다음과 같이 정의할 수 있다. 먼저, IEC 61499 Function Block 아키텍처 모델은

Function Block 아키텍처 모델에 대한 국제 표준으로서, 펑션 블록(Function Block)으로 정의되는 컴포넌트 모
델과 펑션 블록 컴포넌트 모델로부터 만들어지는 컴포넌트들로 구성되는 임베디드 소프트웨어 시스템의 아키텍
처 모델이다.
하드웨어 시스템 모델은 임베디드 하드웨어 시스템에 대한 추상화 모델로서, 임베디드 소프트웨어 시스템이 센
[0027]

펑션 블록 피처(Function Block Feature) 모델은 펑션 블록 피처를 기재할 때 지켜야 할 문법 규칙 및 의미 규

계를 센서-컨트롤러-액추에이터 설계 패턴에 기반을 두고 명시적으로 표현하기 위하여 고안되었다.

추출하고 펑션 블록 아키텍처를 설계하는 작업의 근거가 된다. 또한, 펑션 블록 피처는 펑션 블록 아키텍처의

펑션 블록 컴포넌트는 특정 임베디드 소프트웨어 시스템의 아키텍처 설계 결과 펑션 블록 컴포넌트 모델에 기반
[0031]
을 두고 펑션 블록 컴포넌트 추출 과정을 통해 생성된 구성요소를 의미한다. 이 때 펑션 블록 컴포넌트 모델은
IEC 61499 Function Block 아키텍처 모델을 구성하는 구성요소가 되는 펑션 블록에 대한 컴포넌트 모델이며, 펑
션 블록 컴포넌트를 추출하는 것은 펑션 블록 피처 분석 모델의 펑션 블록 피처들부터 펑션 블록 아키텍처를 구
성하는 펑션 블록 컴포넌트를 추출하는 것을 의미한다.
센서-컨트롤러-액추에이터 패턴은 임베디드 소프트웨어 시스템 설계 시 하드웨어 변화에 따른 소프트웨어 재사
[0032]
용성을 극대화하기 위하여 고안된 임베디드 소프트웨어 시스템 설계 패턴을 의미한다. 임베디드 소프트웨어 컴
포넌트의 설계 과정에서 임베디드 시스템의 하드웨어 기능과 소프트웨어 기능을 동일하게 센서-컨트롤러-액추에
이터로 분류함으로써 하드웨어 구성요소와 소프트웨어 구성요소 간의 연관 관계를 명시적으로 정의할 수 있도록

다음으로, 입력된 하드웨어 스펙을 이용하여 하드웨어 시스템 모델을 생성하기 위한 시스템 분석을 진행할 수

다음으로, 분석된 펑션 블록 피처를 기반으로, 펑션 블록을 구성할 수 있다. 구체적으로, 생성된 펑션 블록 피

정의함으로써 임베디드 소프트웨어 컴포넌트 아키텍처를 설계할 수 있다.

일 실시 예에 따르면, 시스템 분석은 펑션 블록 피처를 적용한 임베디드 소프트웨어 컴포넌트 모델 설계 방법의

하며, 인터럽트 분석은 각 하드웨어 장치의 동작에 의해 발생하는 인터럽트 신호를 분석한다.
하드웨어 시스템 모델 분석에서 활용되는 센서-컨트롤러-액추에이터 패턴은 임베디드 소프트웨어 설계에 자주
[0041]
사용되는 패턴이다. 이 패턴은 개발을 진행할 시스템의 하드웨어 구조를 기반으로 시스템의 컴포넌트를 센서,
컨트롤러, 액추에이터로 구분하여 관계를 정의하고, 하드웨어 시스템 모델을 만들어 소프트웨어를 설계를 진행
한다. 이러한 센서-컨트롤러-액추에이터 패턴을 활용하여 하드웨어 시스템 모델을 분석하면, 개발을 진행할 시

스템 하드웨어 구조로부터 그 구조를 추상화한 모델을 생성할 수 있다. 그리고 생성된 모델을 기반으로 소프트
웨어 설계를 진행하기 때문에 하드웨어와 하드웨어 시스템 모델 사이에 추적 가능성이 보장될 수 있다.
하드웨어 시스템 모델 분석은 개발 대상인 임베디드 시스템의 하드웨어 스펙을 입력으로 하며, 그 시스템의 하
[0042]
드웨어 구조 및 장치들을 추상화함으로써 하드웨어 시스템 모델을 생성한다. 일 실시 예에 따르면, 하드웨어 시
스템 모델은 시스템 분석의 결과물로 센서, 컨트롤러, 액추에이터에 해당하는 하드웨어 모델을 정의하고, 물리
적으로 연결되어 있는 하드웨어 모델을 실선으로 연결하여 관계를 표현할 수 있다. 이와 관련하여, 도 2는 하드
웨어 시스템 모델 분석에 따른 하드웨어 시스템 모델을 나타낸 개념도이다.
도 2를 참조하면, 하드웨어 시스템 모델은 시스템의 하드웨어 장치들을 추상화하여 센서부, 컨트롤러부, 액추에
[0043]
이터부의 3가지 영역으로 구성될 수 있다. 이러한 하드웨어 시스템 모델은 시스템에 구성되어 있는 하드웨어 장
비를 모델로 표현하고, 이들 모델 간 물리적 연결에 대한 관계를 표현함으로써 나타내어 질 수 있다. 이 때의
모델 이름은 장비의 이름 혹은 별칭으로 작성될 수 있다.
일 실시 예에 따르면, 하드웨어 시스템 모델의 구성요소로는 센서, 컨트롤러, 액추에이터 및 인터페이스 모듈이
[0044]
포함될 수 있다. 먼저, 센서는 임베디드 시스템의 컨트롤러의 인터페이스를 통해 장착되는 장치로써 실제 환경
에 존재하는 물리량을 감지하여 전기신호로 변환하는 장치이다. 컨트롤러는 제어장치로서 임베디드 시스템에서
작성된 논리 명령을 수행하기 위해 마이크로프로세서 혹은 마이크로컨트롤러를 포함한다. 이에 따라 컨트롤러는
외부에서 정보를 받아 처리하고 그 처리에 의하여 생성된 데이터를 내보내는 역할을 할 수 있다. 액추에이터는
임베디드 시스템에서 제어 명령에 의해 움직이는 기계 장치이다. 인터페이스 모듈은 임베디드 시스템에서 서로
다른 두 개 이상의 장치 사이에 정보 및 전기신호를 주고받을 수 있도록 지원하는 접점에 해당한다. 이들 구성
요소 간의 관계는 물리적으로 연결되어 있는 두 모델을 실선으로 연결함으로써, 실제 임베디드 시스템의 장치를
기반으로 생성된 두 모델 간의 물리적 연결관계를 링크로 나타낼 수 있다.
일 예시로, 임베디드 시스템이, ON/OFF 기능을 가지고 있는 전조등 스위치에 대해 사용자가 ON/OFF 조작을 하면
[0045]
그에 따라 차량 전조등이 ON/OFF가 되는 기능 요구사항을 지니고 있는 것으로 가정한다. 그 경우, 임베디드 시
스템의 전조등 스위치, 문 열림 감지 센서 및 문 잠금 스위치는 컨트롤러의 인터페이스를 통해 장착되는 장치로
써 물리량을 감지하여 전기신호로 변환할 수 있다. 이에 따라, 전조등 스위치, 문 열림 감지 센서 및 문 잠금
스위치는 센서부(210)에 포함될 수 있다.
또한, 위의 예시에서 임베디드 시스템의 전조등, 문 열림 경고등 및 문 잠금 장치는 각각 센서부(210)의 전조등
[0046]
스위치, 문 열림 감지 센서 및 문 잠금 스위치에 대한 입력에 대응하여 컨트롤러부(220)에서 출력되는 제어 명
령에 의해 움직이는 기계 장치이다. 이에 따라, 전조등 스위치, 문 열림 감지 센서 및 문 잠금 스위치는 액추에
이터부(230)에 포함될 수 있다.
또한, 위의 예시에서 임베디드 시스템의 CPU와 저장매체는 센서부(210)로부터 출력되는 신호를 인터페이스 모듈
[0047]
(221)을 통해 수신하고, 이를 처리하여 생성된 데이터를 출력으로 하여 인터페이스 모듈(222)을 통해 액추에이
터부(230)에 전달할 수 있다. 이에 따라, CPU와 저장매체는 컨트롤러부(220)에 포함될 수 있다.
한편, 도 2를 참조하면, 센서부(210)와 컨트롤러부(220) 및 액추에이터부(230)는 각각의 연결 관계가 실선으로
[0048]
표현된다. 즉, 모델 사이의 실선 표현을 통해, 센서부(210)는 인터페이스 모듈(221)을 통해 컨트롤러부(220)와
통신하고, 액추에이터부(230)는 인터페이스 모듈(222)을 통해 컨트롤러부(220)와 통신하는 것을 알 수 있다.
따라서, 도 2와 같이 임베디드 시스템에 대해 그 구성요소들을 하드웨어 장치들로 추상화하여 센서부, 컨트롤러
[0049]
부, 액추에이터부의 3가지 영역으로 구성한 것을 하드웨어 시스템 모델이라고 할 수 있다.
다음으로 시스템 분석의 일 예로 데이터 타입 분석이 있다. 데이터 타입이란 실제 임베디드 시스템 장치들이 데
[0050]
이터를 생성, 연산 그리고 전달할 때 각 장치의 레지스터 혹은 저장소에 저장되는 데이터의 유형을 의미한다.
하드웨어 장치마다 입력 받거나 출력하는 데이터의 타입이 각각 다를 수 있다. 이러한 특징을 임베디드 소프트
웨어 컴포넌트 모델 설계에 반영하기 위해서는 사전에 데이터 타입에 대한 분석 작업이 필요하다. 예를 들어,
센서가 실제 환경의 물리량을 측정하여 레지스터에 저장하거나 컨트롤러에 전송할 때, 측정한 물리량이 정수이
거나 실수일 수 있다. 마찬가지로, 액추에이터가 동작하기 위해 입력 받고 레지스터에 저장되는 데이터는 정수
이거나 실수일 수 있다. 이러한 하드웨어 특징은 하드웨어의 종류마다 다르므로 별도의 분석 작업이 필요하며,

피처(Feature)는 소프트웨어의 설계를 위한 소프트웨어 분석 방법 중 하나인 피처 분석의 결과물이다. 또한, 피
[0059]
처 분석은 소프트웨어의 기능 요구사항을 분석하여 대상 소프트웨어의 정성적이고 추상적인 특징을 피처로 추출
하는 것이다. 이러한 피처는 개발 대상 소프트웨어의 기능 요구사항과 소프트웨어 설계 요소 간 연결 매개체로
활용될 수 있으며, 피처를 통해 기능 요구사항과 소프트웨어 설계 요소 간 추적 가능성을 확보할 수 있다.
본 개시의 일 실시 예에 따르면, 피처는 임베디드 소프트웨어 시스템 컴포넌트 설계에 활용되어, 시스템 모델과
[0060]
펑션 블록 컴포넌트 간의 추적 가능성을 확보할 수 있는 연결 매개체가 될 수 있다.
펑션 블록 피처 모델은 펑션 블록 피처 분석 결과로 생성된 펑션 블록 피처를 정의한 것이다. 그리고, 펑션 블
[0061]
록 피처 모델은 각 펑션 블록 피처의 구분을 위한 번호, 액션, 입력/출력 데이터 및 입력/출력 이벤트로 정의될
수 있다. 따라서 펑션 블록 피처 모델은 기능 요구사항 ID, FBF(Function Block Feature) 번호, 액션, 입력 데
이터, 출력 데이터, 입력 이벤트 및 출력 이벤트를 포함할 수 있다.
기능 요구사항 ID는 펑션 블록 피처 분석 대상이 되는 임베디드 시스템의 기능 요구사항의 식별번호를
[0062]
의미한다. FBF 번호는 펑션 블록 피처가 생성된 순서로 부여되는 번호이고, 액션은 펑션 블록 피처의 행위를 의
미한다. 입력 데이터는 액션에 대하여 데이터 입력 행위를 하는 장치 및 장치의 저장공간을 구성요소로 하며,
저장소의 이름 또는 별명과 장치의 이름 또는 별명으로 작성될 수 있다.  입력 데이터는 '저장소 이름[장치
이름]'으로 표현될 수 있으며, 예를 들어, Transfer 액션에 대해 데이터 입력 행위를 하는 장치가 전조등 스위
치이고 전조등 스위치의 저장소가 레지스터일 때 입력 데이터는 'SWReg[OnOffSW]'와 같이 표현될 수 있다. 출력
데이터는 액션에 대하여 데이터 출력 행위를 하는 장치 및 장치의 저장공간을 구성요소로 하며, 저장소의 이름
또는 별명과 장치의 이름 또는 별명으로 작성될 수 있다. 출력 데이터는 '저장소 이름[장치 이름]'으로 표현될

예를 들어, Transfer 액션에 대해 인터럽트 영향을 받는 장치가 액추에이터부에 연결되는 인터페이스일 때, 출

추에이터 레지스터에 저장된 제어명령을 수행하는 행위를 의미한다. Calculate는 인터페이스 저장소에 저장된
데이터를 전송 대상 저장소의 데이터타입을 맞추기 위한 행위를 의미한다. Transfer는 특정 하드웨어 모델의 저

표 9는 임베디드 소프트웨어 시스템을 펑션 블록 피처를 기반으로 분석한 결과물로서, 특정 기능 요구사항을 수
[0082]
행하기 위해 액션 별로 입력/출력되는 데이터와 이벤트를 확인할 수 있고, 이를 통해 인터럽트 구간이 언제인지
알 수 있다. 또한, 센서-컨트롤러-액추에이터 패턴을 기반으로 하여 임베디드 소프트웨어 시스템이 펑션 블록
피처 단위로 구분되는 바, 소프트웨어 시스템과 하드웨어 시스템 간의 종속성 확보가 가능하다. 
본 개시에 따른 임베디드 소프트웨어 컴포넌트의 설계 방법에 있어서, 펑션 블록 피처 모델을 정의한 후 펑션
[0083]
블록 컴포넌트의 구조를 설계할 수 있다. 보다 구체적으로, 펑션 블록 피처 모델을 기반으로 펑션 블록 컴포넌
트를 추출하고, 펑션 블록 컴포넌트 사이의 인터페이스를 정의하여, 펑션 블록 컴포넌트 사이의 연결 관계를 설
계할 수 있다. 이 때, 펑션 블록 피처와 펑션 블록 컴포넌트 모델의 구성요소를 상호 연결하기 위한 매핑 규칙
이 필요하다.
이와 관련하여, 도 3은 일 실시 예에 따른 펑션 블록 컴포넌트 모델의 구성요소와 펑션 블록 피처의 관계를 나
[0084]
타낸 개념도이다.
도 3을 참조하면, 펑션 블록 컴포넌트 모델의 구성요소는 타입 이름, 입력/출력 데이터, 입력/출력 이벤트 및
[0085]
알고리즘을 포함한다. 여기서 알고리즘은 실제 논리 연산을 수행하는 코드로서, 펑션 블록 컴포넌트 설계가 끝
난 후 개발자가 필요한 기능을 구현하는 부분에 해당한다.
펑션 블록 컴포넌트 모델에서 타입 이름은 펑션 블록 컴포넌트 모델의 이름이자 유형을 의미한다. 이는 펑션 블
[0086]
록 피처의 액션 유형에 따라 센서, 컨트롤러, 액추에이터 및 인터페이스로 분류될 수 있으며, 펑션 블록 컴포넌
트 모델 타입과 매핑이 가능하다. 또한, 펑션 블록 피처의 입력 데이터, 출력 데이터는 펑션 블록 컴포넌트 모
델의 입력/출력 데이터와 매핑될 수 있으며, 펑션 블록 피처의 입력 이벤트와 출력 이벤트는 펑션 블록 컴포넌
트 모델의 입력/출력 이벤트와 매핑이 가능하다.
일 실시 예에 따르면, 분석된 펑션 블록 피처를 통해 펑션 블록 컴포넌트를 추출하기 위하여, 먼저, 센서, 인터
[0087]
페이스, 컨트롤러 및 액추에이터 역할을 하는 각각의 펑션 블록 컴포넌트 모델을 생성할 수 있다. 그리고 펑션
블록 컴포넌트 모델을 각각 센서 타입, 인터페이스 타입, 컨트롤러 타입 및 액추에이터 타입으로 분류할 수 있
다. 다음으로, 생성된 각각의 센서 타입, 인터페이스 타입, 컨트롤러 타입 및 액추에이터 타입에 펑션 블록 피
처의 액션을 중심으로 입력/출력 데이터 또는 입력/출력 이벤트를 고려하여 펑션 블록 피처를 매핑할 수 있다.
이와 관련하여, 도 4는 일 실시 예에 따른 펑션 블록 피처를 펑션 블록 컴포넌트 모델의 타입에 따라 매핑하는
[0088]
것을 나타낸 개념도이다.
도 4에서 FBF-001의 액션은 Read이고, 이는 센서 장치가 데이터를 감지하여 이벤트가 일어나고 감지한 데이터를
[0089]
